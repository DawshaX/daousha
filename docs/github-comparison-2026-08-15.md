# مقارنة نسخة GitHub والنسخة المحلية — XDAW NOVA

## نطاق المراجعة

راجعت المستودع الخاص [`DawshaX/daousha`](https://github.com/DawshaX/daousha) عبر جلسة المالك، وراجعت سجل التغييرات وبنية الملفات وREADME ومولد الحلقة وسكربت النشر الموحد وسكربت تحديث الجدولة. قارنت ذلك بالنسخة المحلية الحالية لمنصة XDAW NOVA. لم أستنسخ المستودع ولم أشغل أي سكربت منه، ولم أنقل أو أدمج أي ملف.

> **الحكم المختصر:** النسخة المحلية الحالية هي الأفضل كأساس دائم وآمن للمنتج. نسخة GitHub أقوى كـ«خط إنتاج عملي سريع» ومصدر لأفكار التشغيل، لكنها لا تصلح للدمج المباشر لأن سكربتاتها تتجاوز حواجز الحقوق والمراجعة وسياسة النشر في المنصة المحلية.

## ما أضفته نسخة GitHub

| الإضافة | ما وجدته | القيمة العملية |
|---|---|---|
| مكتبة موضوعات | `scripts/topic_library.json` تضم حلقات منشورة وأخرى في طابور الإنتاج بعناوين وزوايا قصيرة | **مفيد جدًا** كمصدر أفكار يمكن استيراده إلى استوديو المشاريع |
| تشغيل حلقة | `produce_next_episode.py` يختار حلقة، يتحقق من وجود سيناريو وتعليق و4 مشاهد، ثم يستدعي بناء الفيديو | مفيد كتصور لخط أنابيب إنتاج، لكنه يعتمد على ملفات ومسارات محلية ثابتة |
| بناء فيديو رأسي | وجود `build_episode.sh` ومسار موثق لتجميع 4 مشاهد وتعليق صوتي في فيديو 9:16 | فكرة قابلة للنقل لاحقًا ضمن عامل إنتاج محكوم، لا كسكربت حر |
| نشر متعدد المنصات | `publish_all.py` يرفع إلى YouTube وFacebook ويرسل Telegram، ويترك Instagram لمسار منفصل | يثبت تقدمًا تشغيليًا، لكنه غير كافٍ كناشر مركزي آمن |
| توثيق عمليات | سجل حلقات، playbook، وسلّم تصاعد للنشر وخطة شهرية | مفيد كسجل تاريخي ومرجع محتوى، مع ضرورة التحقق من كل حالة في APIs الرسمية |
| صيانة SEO | أحدث الالتزامات تشير إلى إعدادات قناة وSEO وسكربتات تحديث YouTube | جدير بالاستخلاص كمحرر مسودات بيانات وصفية داخل المنصة، لا كتعديل مباشر للحساب |

تسجل README في GitHub ادعاءات بنشر أربع حلقات على YouTube وInstagram وFacebook؛ تعاملت معها كسجل موثق من المستودع لا كتحقق مستقل من كل منصة. [1]

## عناصر لا أنصح بدمجها كما هي

| العنصر | السبب |
|---|---|
| القراءة المباشرة من `/home/ubuntu/secrets.txt` | تشتت الأسرار خارج إدارة متغيرات البيئة وخزنة المشروع، وتزيد خطر التسرب |
| الرفع العام افتراضيًا في `publish_all.py` | يبدأ YouTube بخصوصية `public` من دون معاينة أو قرار حقوق أو تأكيد منشور |
| نشر YouTube وFacebook بلا سجل قرار موحد | قد يؤدي فشل منصة واحدة إلى نتائج جزئية وإعادة تشغيل تسبب تكرار منشورات |
| تمثيل Instagram كمنشور مكتمل | الدالة الحالية تعيد `IG_VIA_SCHEDULED_SHELL` بدل تنفيذ رفع Instagram في نفس المعاملة |
| cron في `update_schedule.py` | القيمة `0 6,12,18,0 * * *` لا توافق صيغة الستة حقول التي تعتمدها جدولة المنصة الحالية، ولا تمرر منطقة زمنية صريحة |
| المسارات والهوية الثابتة | الاعتماد على `/home/ubuntu/test_run` وPage ID ثابت يجعل النقل والتشغيل الإنتاجي هشًا |

## ما يستحق نقله إلى النسخة المحلية

| الأولوية | الإضافة المقترحة | طريقة نقل آمنة |
|---|---|---|
| 1 | مكتبة الموضوعات | استيرادها كمشاريع `idea` أو طابور أفكار مع مصدر وتقييم حقائق وحقوق، من دون نسخ حالة `published` تلقائيًا |
| 2 | قالب الحلقة القصيرة | تحويل «سيناريو + تعليق نصي + 4 مشاهد + غلاف» إلى قالب مشروع داخل الاستوديو، مع مهام ظاهرة للمستخدم |
| 3 | قوالب SEO | حفظ عناوين وأوصاف ووسوم مقترحة كـ **مسودة رفع خاصة** داخل مكتب النشر، مع مراجعة وتأكيد مستقلين |
| 4 | سجل الحلقات | إضافة استيراد يدوي موثق للروابط المنشورة بعد التحقق من المصدر الرسمي، ليغذي التحليلات الفعلية |
| 5 | سلم النشر | نقل فكرة التدرج إلى سياسة النشر الحالية كحدود قابلة للضبط، لا كزيادة آلية لمجرد مرور الوقت |
| 6 | عامل بناء الفيديو | تصميمه لاحقًا كخدمة إنتاج محكومة بالمهام والملفات، مع فحص حقوق كل أصل وحفظ نتيجة قابلة للمراجعة |

## التوصية العملية

اعتمد **النسخة المحلية الحالية باعتبارها القلب الرسمي**: هي الأنسب للاستمرار، لأنها تحافظ على فصل الحسابات، وحقوق المحتوى، والمراجعة البشرية، وسجل القرارات، والتفويضات الرسمية. خذ من GitHub **المحتوى وخبرة التشغيل والقالب الإنتاجي**، لكن لا تأخذ منه سكربت النشر المباشر أو إدارة الأسرار أو cron كما هي.

الخطوة الذكية التالية هي تنفيذ **مستورد مكتبة موضوعات GitHub** إلى استوديو المشاريع: يعرض الحلقات السابقة والمواضيع المتبقية، يطلب اعتماد المصدر، ويحوّل كل موضوع مختار إلى حزمة Short + Long قابلة للمراجعة. هذا يعطيك أفضل ما في النسختين بلا الرجوع إلى النشر غير المحكوم.
