# DAWSHA Operational Architecture

## الخيار التشغيلي المعتمد

يعتمد DAWSHA حاليًا على **WebDev Autoscale** مع قاعدة البيانات ومهام **Heartbeat** الدورية، لا على عملية خادم دائمة أو جهاز افتراضي مستقل. هذا يناسب دورة الرصد الحالية لأنها تستيقظ عبر طلبات HTTP دورية، تحفظ كل حالة في قاعدة البيانات، ثم تنتهي؛ فلا تعتمد على ذاكرة عملية حية أو متصفح أو جلسة محلية.

| المكوّن | الحالة | المسؤولية |
| --- | --- | --- |
| واجهة وخادم DAWSHA | WebDev Autoscale | لوحة التحكم، tRPC، السياسات، السجل، والحواجز |
| مهمة `dawsha-trend-intake` | Heartbeat كل 6 ساعات | إدخال فكرة بحث واحدة كحد أقصى خلال 20 ساعة |
| قاعدة البيانات | MySQL مُدار | المشاريع، `workflowTasks`، حالة المهمة، وسجل التغييرات |
| الفيديو والنشر | خارج دورة الرصد | لا يبدأان إلا بعد الأصول والحواجز وقرار المسار القائم |

## التكلفة والحدود

هذا الخيار هو المسار **المجاني للبدء** ولا يتطلب شراء نطاق أو خادم دائم. لكن منصة الاستضافة قد تطبق استخدامًا محسوبًا عند أحجام تشغيل أعلى، ولذلك لا يدّعي النظام أن توليد النماذج أو المعالجة الثقيلة بلا حد أو بلا تكلفة. تركنا مرحلة السكربت التلقائي متوقفة حتى يُختار لها سقف استعمال واضح؛ أما الرصد الحالي فلا يستدعي نموذجًا.

لا يحتاج DAWSHA حاليًا إلى Reserved Hosting أو Cloud Computer: لا توجد جلسات WebSocket حالةُها في الذاكرة، ولا Docker، ولا متطلبات نظامية خاصة. إذا تطلبت مرحلة مستقبلية تحويل فيديو طويلًا أو عاملاً متصلاً دائمًا أو معالجة تتجاوز حد WebDev، تُقيَّم هذه الحاجة منفصلة قبل الانتقال إلى بنية مدفوعة.

> تضمن دورة الرصد الاستمرارية المجدولة، لا وجود عملية واحدة تعمل لحظة بلحظة على مدار الساعة. مصدر الحقيقة هو قاعدة البيانات؛ لذلك يمكن للمهمة استئناف العمل بعد إعادة تشغيل خدمة أو تبدل مثيل Autoscale.
